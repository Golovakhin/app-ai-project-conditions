# ADR 001: Фреймворк агентов и дизайн первого Tool

**Статус:** Принято
**Дата:** 2026-10-19
**Команда:** Головахин Андрей Валерьевич, Савченко Станисла Алексеевич, Монахов Георгий Алексеевич
**Проект:** app-ai-project-conditions

## Контекст

Помощник команды живёт в отдельном репозитории `app-ai-project-conditions`
со своим окружением, `.env` и зависимостями. На практике 1 нужно было
решить три задачи:

1. Настроить конфигурацию AI-слоя так, чтобы провайдер LLM, имя модели,
   адрес и ключ не лежали в коде и менялись правкой `.env`.
2. Реализовать первый Tool по спецификации, защищённой на воркшопе 1,
   с валидацией входа и безопасным возвратом ошибки: неверный вход
   должен возвращаться агенту текстом, по которому он может исправиться,
   а не ронять процесс необработанным исключением.
3. Собрать контур «агент → Tool → ответ» и сохранить трассы, в которых
   видно, что агент реально вызвал Tool, а не придумал ответ.

Ограничения, заданные курсом и средой:

- локальная модель работает без интернета (Ollama, `qwen3:4b-instruct`);
- нужен запасной путь через облачного провайдера с OpenAI-совместимым API,
  переключение — только правкой `.env`, без изменения кода;
- `.env` не должен попадать в Git, ключ не должен печататься в консоль
  и в логи;
- Tool на этой практике учебный и не обращается к коду бэкенда: `math_condition`
  проверяет число по аргументам, поэтому ограничение «бэкенд только читается»
  к нему не применяется. Это надо зафиксировать честно, чтобы ревьюер
  не искал в проекте `AI_REPO_ROOT` и эталонный `find_endpoint`.

## Рассмотренные варианты

### Конфигурация AI-слоя

- **`os.getenv` вручную.** Плюс: без дополнительных зависимостей.
  Минус: нет валидации типов; опечатка `LLM_PROVIDER=olama` всплывёт
  поздно, уже внутри агента; `repr` настроек напечатает ключ целиком.
- **`pydantic-settings`.** Плюс: валидация при старте, `Literal` для
  провайдера, `SecretStr` для ключа, `extra="ignore"` для чужих переменных
  в общем `.env`. Минус: дополнительная зависимость (уже зафиксирована
  в `requirements-ai.txt`).

Выбрали `pydantic-settings`.

### Формат возврата ошибки из Tool

- **Исключение.** Плюс: привычно для Python. Минус: необработанный traceback
  роняет запуск агента; модель не видит текста, по которому можно исправиться.
- **JSON-строка с `status: "error"`.** Плюс: агент читает сообщение и может
  повторить вызов с исправленными аргументами; формат одинаков при успехе
  и при ошибке. Минус: нужно дисциплинированно возвращать `_fail(...)`
  во всех ветках и следить, чтобы ни один путь не выбрасывал исключение.

Выбрали JSON-строку.

### Валидация `condition` в `math_condition`

- **Свободная строка.** Плюс: минимум кода. Минус: модель может передать
  `super-positive`, и Tool либо упадёт, либо вернёт невнятную ошибку.
- **Перечисление допустимых значений.** Плюс: сразу отсекает неверный вход,
  а сообщение перечисляет допустимые значения и подсказывает исправление.
  Минус: список надо синхронизировать с docstring и контрактом.

Выбрали перечисление `positive`, `negative`, `zero`, `even`, `odd`.

### Фреймворк агентов

- **Свой цикл на LangChain.** Плюс: полный контроль. Минус: нужно вручную
  обрабатывать парсинг tool call, бесконечные циклы, ошибки; много шаблонного
  кода; на паре это не успеть.
- **CrewAI.** Плюс: готовый цикл ReAct, декларативные `Agent`/`Task`/`Crew`,
  `@tool` из `crewai.tools`, `max_iter` как страховка от зацикливания.
  Минус: часть деталей скрыта, отладка идёт по трассе, а не по шагам кода.

Выбрали CrewAI: он задан курсом и даёт рабочий контур за время пары.

## Решение

### Конфигурация

- `ai/config.py` на `pydantic-settings`, `SettingsConfigDict(env_file=".env",
  env_file_encoding="utf-8", extra="ignore")`.
- Провайдер — `Literal["ollama", "cloud"]`; опечатка падает при старте
  с понятным текстом.
- Ключ — `SecretStr`; настоящее значение отдаётся только через
  `.get_secret_value()` в `llm_factory.py`.
- Все переменные из `config.py` перечислены в `.env.example`; `.env`
  в `.gitignore` и в diff PR отсутствует.

### Единственная точка создания LLM

- `ai/llm_factory.py::get_llm()` — единственное место, где создаётся `LLM`.
- Для Ollama: `model=f"ollama/{settings.ollama_model}"`,
  `base_url=settings.ollama_base_url`.
- Для облака: `model=f"openai/{settings.cloud_model}"`,
  `base_url=settings.cloud_base_url`, `api_key=...`,
  `project=settings.cloud_project or None`.
- Смена провайдера — правка `.env`; код не меняется.

### Контракт Tool `math_condition`

| Что | Решение |
|---|---|
| Имя для модели (аргумент `@tool`) | `math_condition` |
| Назначение (одно предложение из docstring) | «Проверяет, удовлетворяет ли число заданному математическому условию»; вызывать, когда пользователь спрашивает «чётное ли число», «больше ли нуля», «равно ли X» |
| Вход | `value: float` — обязателен, любое число; `condition: str` — обязателен, одно из `positive`, `negative`, `zero`, `even`, `odd` |
| Выход при успехе | `{"status": "ok", "value": ..., "condition": ..., "result": true/false}` |
| Выход при ошибке | `{"status": "error", "message": "<что не так и что исправить>"}` |
| Пустой результат | Не применимо: `result: false` — это успешная проверка, а не ошибка |
| Откуда данные | Не читает бэкенд; считает по аргументам |
| Конфигурация LLM | `pydantic-settings`, `.env`, `get_llm()` |

Краевые случаи, которые Tool возвращает строкой:

- неизвестное `condition` — ошибка с перечислением допустимых значений;
- `value` не приводится к числу — ошибка с указанием, что получено;
- нецелое `value` для `condition in {"even", "odd"}` — ошибка
  «`condition='even' требует целое число, получено 3.5`».

### Правило безопасного возврата

Тело Tool не выбрасывает исключений: любая ошибка возвращается JSON-строкой
через `_fail(...)`. Формат ответа одинаков при успехе и при ошибке: всегда
`str` с JSON внутри и полем `status`.

Отдельный исход — проверка схемы аргументов самим CrewAI до тела Tool:
если обязательный аргумент не передан или пришёл не того типа, вызов
отклоняется фреймворком (`ValueError: ... arguments validation failed`,
`Field required`). Это не нарушение безопасного возврата: наш код до него
не доходит, и в `_check.py` такие вызовы не включаются.

### Проверка Tool без LLM

`ai/tools/_check.py` запускается командой `python -m ai.tools._check`
и печатает имя инструмента, строку `ok` для корректного входа и строку
`error` для некорректного. Traceback быть не должно. Файл остаётся
в репозитории: ревьюеры соседней команды запускают его сами.

## Последствия

### Что стало проще

- Провайдер переключается одной правкой `.env`; `ai/llm_factory.py` —
  единственное место, которое знает про модель и адрес.
- Ошибки Tool безопасны: агент получает текст, по которому может
  исправиться, и не падает. Это видно в `run-02.log` и `run-04.log`.
- Tool проверяется без LLM через `_check.py`, поэтому вторая машина
  и ревьюеры могут проверить его без запуска модели.

### Чем за это платим

- `math_condition` не работает с кодом бэкенда: он не проверяет реальные
  эндпоинты и не читает файлы. Это ограничение учебной спецификации
  воркшопа 1, и в цикле 2 его придётся заменить или дополнить Tool
  над бэкендом.
- `math_condition` — простая детерминированная функция; она не показывает,
  как Tool поведёт себя на больших данных, файлах и каталогах.
- Локальная 4b-модель слабее в function calling, чем облачная: при
  неконкретной задаче она может не вызвать Tool. Это видно в `run-03.log`,
  где агент попросил уточнить число вместо вызова Tool — допустимый,
  но не единственно возможный исход.
- CrewAI скрывает часть шагов цикла; отладка идёт по трассе `verbose=True`
  и по `max_iter`, а не по коду фреймворка.

## Наблюдения из трассы

Логи лежат в `ai/traces/`.

- `run-01.log`: Tool вызван с `{'value': 42, 'condition': 'even'}`,
  вернул `{"status": "ok", "value": 42.0, "condition": "even", "result": true}`,
  агент ответил «Число 42 является чётным». Tool вызван ровно один раз.
- `run-02.log`: Tool вызван с `condition='super-positive'`, вернул
  `{"status": "error", "message": "condition должен быть одним из
  ['even', 'negative', 'odd', 'positive', 'zero'], получено 'super-positive'"}`.
  Процесс не упал, агент пересказал ошибку и перечислил допустимые значения.
  Это сценарий 1 шага 3.3.
- `run-03.log`: значение не указано; агент не вызвал Tool и попросил
  уточнить число — допустимый исход сценария 2 шага 3.3.
- `run-04.log`: Tool вызван с `{'value': 3.5, 'condition': 'even'}`,
  вернул `{"status": "error", "message": "condition='even' требует целое
  число, получено 3.5"}`. Процесс не упал, агент объяснил, что проверка
  невозможна. Это проверка краевого случая «нецелое для even/odd».
- Облачная модель на момент написания ADR не проверялась: `run-cloud.log`
  нет, полное переключение провайдера осталось на домашнее задание
  (п. 2 ДЗ).

Отдельно фиксируем расхождение: текущий `ai/run_agent.py` содержит задачу
про `value=3.5`, а `run-01.log` — про `value=42`. Лог не воспроизводится
из текущего кода. Это надо либо исправить (привести `run_agent.py`
к сценарию из `run-01.log` или перезапустить агент и обновить лог),
либо явно объяснить в PR. В ADR фиксируем как известное расхождение,
которое закрывается до слияния.

## Когда пересмотреть

Решение пересматривается, если:

1. Tool начнёт читать реальный код бэкенда (файлы, каталоги) — появятся
   ограничения доступа, которые сейчас не нужны.
2. Число инструментов вырастет и понадобится оркестрация нескольких
   агентов или делегирование задач.
3. Локальная модель перестанет справляться с function calling и облачный
   провайдер станет обязательным, а не запасным.
4. Появятся требования к скорости ответа, при которых время запуска
   CrewAI и локальной модели станет критическим.
5. CrewAI изменит API `@tool` или параметры `LLM` между мажорными
   версиями — версия закреплена в `requirements-ai.txt`, и обновление
   будет отдельным решением.
